# Verified integration facts

Verified 2026-11-09 against the following primary documentation:

- `getEvents` accepts `filters`; each filter matches both contract and topics, with a maximum of **5 filters** and **5 contract IDs** per request. Topic matchers contain one to four segments. The response includes `events`, `latestLedger`, `oldestLedger`, close times, and an opaque `cursor`. Events have a unique `id`, ledger, contract ID, topic ScVals, and value ScVal in base64 XDR. [Stellar getEvents](https://developers.stellar.org/docs/data/apis/rpc/api-reference/methods/getEvents)
- RPC pagination uses an opaque cursor returned by the previous page. `getEvents` permits a hard-coded limit from **1 through 10,000**, default **100**. A cursor request omits `startLedger` and `endLedger`, as required by the method reference. The docs do not promise cursor stability across node restarts; Eventide therefore persists and replays safely by event ID. [Pagination](https://developers.stellar.org/docs/data/apis/rpc/api-reference/structure/pagination)
- The method reference states that `startLedger` below the node's oldest ledger or above its latest ledger is an error. A Stellar RPC issue records the observed error as JSON-RPC code **-32600**, message **`start is before oldest ledger`**, and directs clients to use `getHealth` for the RPC node's actual oldest ledger. Eventide recognizes that exact documented/observed form. [getEvents](https://developers.stellar.org/docs/data/apis/rpc/api-reference/methods/getEvents) [RPC issue](https://github.com/stellar/stellar-rpc/issues/260)
- `getHealth` returns `status`, `latestLedger`, `oldestLedger`, and `ledgerRetentionWindow`; the docs define a full window as `latestLedger - oldestLedger + 1`. The stock default shown in the reference is 120,960 ledgers, about seven days depending on cadence, but deployments can configure different windows. [getHealth](https://developers.stellar.org/docs/data/apis/rpc/api-reference/methods/getHealth)
- `getNetwork` returns the node's configured network `passphrase`. Eventide checks every configured endpoint before indexing. [getNetwork](https://developers.stellar.org/docs/data/apis/rpc/api-reference/methods/getNetwork)
- The maintained package for Node.js Soroban RPC and XDR is `@stellar/stellar-sdk`. The current API exposes `xdr.ScVal.fromXdr(Uint8Array)`; Eventide passes decoded base64 bytes to that API and stores the original XDR if decoding fails. [SDK package](https://www.npmjs.com/package/@stellar/stellar-sdk) [SDK API docs](https://stellar.github.io/js-stellar-sdk/)
- Fastify was selected over Hono because its official documentation provides first-class Node.js TypeScript setup and its current v5 documentation includes TypeScript types and validation guidance. [Fastify TypeScript](https://fastify.dev/docs/latest/Reference/TypeScript/)
- Archive capability is not a field standardized by the Soroban RPC method reference. Provider documentation can describe endpoint-specific history, authentication, and retention; for example, Validation Cloud documents a Stellar RPC endpoint and its API-key URL format, but does **not** make a universal archive guarantee. Eventide therefore requires an explicit operator `archiveCapable: true` flag and does not infer capability from a provider name. [Validation Cloud getEvents](https://docs.validationcloud.io/nodeapi/stellar/stellar-rpc-formerly-soroban-api/getevents)

Anything not verified: no provider-wide, portable definition of “archive-capable” was found. The configuration flag is an explicit operator assertion and should only be enabled after checking the provider's own contract and testing an old ledger on that endpoint. Cursor stability guarantees across upgrades were also not found in the public pagination reference.
